Choix des technologies et architecture de l’application

1. Introduction
   Dans le cadre du développement de notre application mobile de suivi d’entraînement personnalisé basé sur le cycle menstruel, plusieurs contraintes techniques ont été identifiées. Parmi celles-ci, la nécessité d’un suivi GPS en temps réel, la gestion d’une authentification sécurisée, l’implémentation d’une logique métier personnalisée intégrant le cycle et les recommandations, ainsi que l’envoi de notifications push quotidiennes. L’objectif étant de réaliser un développement rapide dans une logique MVP, une stack technique cohérente et adaptée a été sélectionnée pour répondre efficacement à ces besoins tout en permettant une mise en œuvre efficace et évolutive.
2. Choix des technologies
   2.1 Application mobile : React Native avec Expo
   Le choix de React Native s’est porté principalement sur la volonté de développer une application cross-platform, compatible à la fois sur iOS et Android, avec une seule base de code. L’utilisation d’Expo vient renforcer cette décision en simplifiant considérablement l’accès aux fonctionnalités natives du téléphone, notamment pour le suivi GPS en temps réel, qui est rendu possible via les API fournies par Expo. Cela permet de collecter les coordonnées utilisateur à intervalles réguliers sans nécessiter une implémentation native complexe. La gestion des notifications push est facilitée grâce à l’intégration avec Firebase, tandis que le stockage sécurisé du token JWT est assuré via les mécanismes natifs tels que Keychain sur iOS ou Keystore sur Android. Ce choix technique accélère le développement, ce qui est cohérent avec l’objectif MVP, tout en répondant efficacement aux contraintes mobiles.
   2.2 Backend : Node.js avec Fastify
   Le backend repose sur Node.js, un choix motivé par la cohérence avec le langage JavaScript utilisé côté front, ce qui facilite la maintenance et accélère le développement. Node.js offre également une excellente réactivité pour la gestion des API REST, essentielles pour notre application. Le framework Fastify a été privilégié par rapport à Express pour ses performances supérieures, particulièrement adaptées aux nombreux appels liés aux sessions d’entraînement. De plus, Fastify intègre nativement un système de validation des données basé sur des schémas JSON, garantissant la conformité des entrées telles que l’email, le cycle ou le poids. Son architecture modulaire via des plugins facilite la maintenance et l’évolution du backend, tout en respectant les exigences de sécurité et de performance du projet.
   2.3 Base de données : PostgreSQL
   PostgreSQL a été choisi comme système de gestion de base de données relationnelle en raison de ses capacités à gérer des relations complexes entre entités telles que les utilisateurs, les sessions ou le cycle menstruel. Il permet également d’effectuer des calculs statistiques comme la distance totale ou la moyenne, tout en assurant la gestion de contraintes fortes, notamment l’unicité et les clés étrangères. La prise en charge native des UUID par PostgreSQL correspond parfaitement au modèle de données défini, rendant ce SGBD particulièrement adapté aux besoins du projet.
   2.4 ORM : Drizzle
   L’ORM Drizzle a été sélectionné pour faciliter l’interaction avec la base de données tout en conservant un contrôle précis sur les requêtes. Sa conception légère, proche du SQL, et sa forte typisation permettent de limiter les erreurs tout en évitant une complexité excessive. Ce choix offre un bon compromis entre abstraction et contrôle, ce qui est essentiel pour garantir la fiabilité et la maintenabilité du code.
   2.5 Authentification : JWT et bcrypt
   L’authentification repose sur l’utilisation de JWT (JSON Web Token) pour gérer les sessions de manière stateless, ce qui est particulièrement adapté aux applications mobiles. Chaque requête inclut un token d’authentification dont la durée de validité est limitée à 7 jours. La sécurité du stockage du token est assurée via les mécanismes natifs du système d’exploitation. Par ailleurs, bcrypt est utilisé pour le hachage des mots de passe, garantissant une protection efficace contre les attaques potentielles.
   2.6 Notifications : Firebase Cloud Messaging
   Firebase Cloud Messaging (FCM) a été choisi pour l’envoi de notifications push, en raison de sa compatibilité multi-plateforme, de sa simplicité d’intégration avec Expo, et de sa gratuité dans le cadre d’un MVP. Il permet d’envoyer facilement des notifications quotidiennes, notamment pour les recommandations d’entraînement, tout en assurant une gestion efficace des messages.
   2.7 Infrastructure : Railway
   Railway a été retenu pour héberger le backend et la base de données, grâce à sa simplicité de déploiement et à sa gestion intégrée de PostgreSQL. Cette solution facilite la séparation entre les environnements de développement (staging) et de production, permettant ainsi une chaîne de déploiement cohérente et sans complexité excessive. Cela contribue à assurer une gestion efficace et fiable de l’infrastructure.
3. Architecture de l’application
   3.1 Type d’architecture
   L’application repose sur une architecture client-serveur de type REST, composée de trois couches principales : une application mobile en tant que client, une API backend qui gère la logique métier et la communication, et une base de données pour le stockage des données. Les échanges entre ces composants se font via le protocole HTTP sécurisé, avec une authentification par JWT pour garantir la sécurité et la cohérence des interactions.
   3.2 Architecture backend
   Le backend suit une architecture en couches, avec une séparation claire entre les routes (contrôleurs), qui gèrent les requêtes HTTP, les services qui implémentent la logique métier (calcul du cycle, recommandations, distance), et l’accès aux données via l’ORM. Cette organisation facilite la maintenance, l’évolutivité et la compréhension du code, tout en permettant une évolution aisée du système.
   3.3 Gestion du temps réel
   Le suivi des séances de running repose sur une approche hybride où le mobile gère en temps réel le GPS, la distance et la durée, tandis que le backend effectue les calculs finaux et la persistance des données. Cette approche permet de réduire la charge serveur, d’optimiser les appels réseau, et d’améliorer l’expérience utilisateur en assurant une réactivité optimale.
   3.4 Gestion du cache
   Certaines données, comme le profil utilisateur, sont mises en cache côté mobile pour réduire le nombre d’appels API, améliorer les performances et offrir une meilleure réactivité. Cela permet d’optimiser l’utilisation des ressources et d’assurer une expérience fluide, même en cas de connexion limitée ou instable.
